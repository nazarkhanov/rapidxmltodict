# Reproducing the parser architecture comparison

The `architecture-*` files are a separate experiment. Existing
`standalone-*`, `upstream-*`, and pre-optimization reports remain intact.
The current baseline is the integrated `e911c9a5dbdc75974e66120861adc38dc36a39b8`
implementation, not one of the older baseline labels in those archived reports.

## Four variants

1. **Current baseline:** frozen e911 source tree and its previously built extension,
   using `rapidxmltodict.parse`.
2. **Iterative DOM/default:** frozen iterative parser/DOM converter,
   using `rapidxmltodict.parse`. In-memory default strings/bytes take the iterative
   DOM path. Binary files and item callbacks still take that snapshot's existing
   Python event mapper. Its callback numbers must not be labeled “DOM streaming.”
3. **Native direct events:** frozen candidate tree, explicitly selected using the
   private `rapidxmltodict._parse._parse_native_events` wrapper. It builds Python
   dictionaries directly from native events. This benchmark does not infer that
   the public default selects this architecture.
4. **Reference:** unmodified `xmltodict==1.0.4`, using its public API and Expat.

The harness allows a different private entry point and JSON keyword options
with `--events-entrypoint`, `--events-options`, `--iterative-entrypoint`, and
`--iterative-options`. These selections are recorded in raw metadata. Do not
silently monkey-patch a public function or let a supposedly forced architecture
fall back to a different backend.

## Prepare immutable snapshots

Use one interpreter and compiler for all variants. Keep the original baseline
binary before editing/rebuilding the candidate. Build candidates separately:

```sh
python -m venv .venv-bench
. .venv-bench/bin/activate
python -m pip install setuptools wheel 'xmltodict==1.0.4'
(cd "$ITERATIVE_ROOT" && CC=gcc CXX=g++ python setup.py build_ext --inplace --force)
(cd "$EVENTS_ROOT" && CC=gcc CXX=g++ python setup.py build_ext --inplace --force)
```

`BASELINE_ROOT`, `ITERATIVE_ROOT`, and `EVENTS_ROOT` should point to independent,
frozen source trees with their extensions under `src/rapidxmltodict/`. The raw
files contain SHA-256 hashes of every runtime source/header and native extension
at the start and end. An implementation change during measurement invalidates
the run. Workers also check the hash of the actual imported extension.

For this experiment the archived baseline has a previously disclosed CRLF/LF
vendor-header difference from its Git representation. Its exact original
on-disk bytes and binary are preserved; their recorded hashes, rather than a
claim that a freshly normalized checkout is byte-identical, identify the
measured baseline. A new build may have a different binary hash even when it is
semantically equivalent. Record that distinction when reproducing.

## Run

Run on Linux with `/proc`, enough RAM for the complete dictionaries, and a stable
CPU allocation. Avoid concurrent builds/tests or other CPU-heavy work. All
workers pin to one CPU, selected with `--cpu` or defaulting to the lowest allowed
CPU. The same selection applies to every architecture. The orchestrator's
rotation prevents one variant from consistently running first.

```sh
python benchmarks/architecture-test-harness.py
python benchmarks/architecture-benchmark.py \
  --baseline "$BASELINE_ROOT" --iterative "$ITERATIVE_ROOT" \
  --native-events "$EVENTS_ROOT" --suite standard \
  --output benchmarks/architecture-standard.json
python benchmarks/architecture-benchmark.py \
  --baseline "$BASELINE_ROOT" --iterative "$ITERATIVE_ROOT" \
  --native-events "$EVENTS_ROOT" --suite large --sizes 10 50 100 \
  --output benchmarks/architecture-large-memory.json
python benchmarks/architecture-derive-memory.py \
  benchmarks/architecture-standard.json benchmarks/architecture-large-memory.json
python benchmarks/architecture-report.py \
  benchmarks/architecture-standard.json benchmarks/architecture-large-memory.json \
  --output benchmarks/architecture-results.md
```

The default uses three fresh workers per variant/workload, nine calibrated
batches per standard worker, and a 3 GiB per-worker address-space cap. Fixtures
are generated by a separate process before any measured worker starts. Records
and large-text bytes come from the existing deterministic generator, so their
10/50/100 MiB hashes can be compared with the archived reports. Inputs are kept
under the system temporary directory by default, not committed to Git.

`--workloads` selects named cases for development smoke checks, but a subset must
not be published as the full comparison. `--repetitions`, `--samples`,
`--batch-seconds`, `--limit-mib`, and `--timeout` are recorded or reflected in raw
sample metadata. Keep all four architectures on identical parameters.

## Workloads and what they show

- Standard: 6/600/6,000 catalog records, mixed Unicode/content, and bytes input.
- Deep: 128, 300, 1,500, and 10,000 nested elements, without modifying Python's
  recursion limit. The output fingerprint itself is iterative.
- Late deep: a 1,500-element branch after 6,000 or 60,000 completed shallow
  siblings. This catches a depth-limit failure that causes the baseline to
  abandon earlier DOM work and reparse the whole document as events.
- 10/50/100 MiB catalog records: direct string results, direct file results,
  discard callbacks, and application-retained callbacks.
- 10/50/100 MiB large text: direct string and file results. Event parsing cannot
  make an inherently large text value disappear from a complete result.

A direct result keeps the full dictionary alive at the memory sample. A discard
callback keeps only scalar count/identifier checksums. A retaining callback
keeps every item in a list. The callback file cases use the same callback code
and item depth for every parser; these are different application retention
choices, not interchangeable output contracts.

## Timing, memory and correctness

Standard RSS is sampled on the first parse of a fresh worker. Only afterward
are the output fingerprint and warmed timing batches run. Standard timing
includes output destruction; large fresh-process timing does not. Binary-file
reading is timed, while in-memory input loading is not. The harness does not evict
the OS page cache; file timings characterize local cached reads plus parsing,
not cold-storage throughput.

Report all of these, rather than only a favorable memory figure:

- baseline current RSS and baseline high-water RSS after import/input loading;
- total process peak RSS;
- incremental peak over pre-parse **current** RSS, derived from each sample;
- the original incremental peak over baseline **high-water** RSS, preserved too;
- retained current RSS with input and result/application-held items alive;
- retained current increase over baseline current RSS.

These are whole-process native-aware RSS values. They are not Python-only
`tracemalloc` totals or precise attribution of bytes to output objects. Large
input-loading transients can raise the baseline peak and make incremental growth
look small. The added current-baseline view exposes that distinction without
remeasuring or changing any original samples. Both per-sample differences are
summarized by their medians, rather than subtracting independently calculated
medians. The report displays both pre-parse baselines, both peak differences,
and the signed retained-current increase. RSS is sampled before fingerprinting
allocates additional state.

Every direct output gets a full typed SHA-256 traversal, including sorted mapping
keys, list order, all text, and `None`. Separate untimed callback integrity passes
hash every emitted item and path without storing all items. Measured callbacks
check every identifier with counts, first/last IDs, sum and squared sum. All four
variants must match the reference. An error or mismatch stops the run and keeps
the partial raw result for diagnosis; a partial result is not a passing benchmark.

The memory guard skips estimated peaks above 40% of available RAM or 80% of the
address-space cap. It does not retry allocation failures with larger limits.
Skipped/failed cases remain visible in raw data and in the generated report.

Raw output intentionally uses relative runtime file names and content hashes,
not absolute local paths, usernames, machine/environment IDs, or executable
paths. The reports include complete trial ranges and preserve the original
baseline names so earlier measurements are not overwritten or relabeled.

## Archived first native-mapper smoke check

[architecture-pre-optimization-results.md](architecture-pre-optimization-results.md)
and its two linked raw files preserve build3's initial performance before the
native mapper's strict-default optimization. They contain 52 measured workers,

## Verify the selected final public dispatcher

After freezing and measuring the final native-event candidate, independently
verify the public API's chosen routes without instrumentation in timed workers:

```sh
python benchmarks/architecture-verify-dispatch.py \
  --candidate "$EVENTS_ROOT" \
  --results benchmarks/architecture-standard.json benchmarks/architecture-large-memory.json \
  --output benchmarks/architecture-public-routing.json
python benchmarks/architecture-report.py \
  benchmarks/architecture-standard.json benchmarks/architecture-large-memory.json \
  --public-routing benchmarks/architecture-public-routing.json \
  --output benchmarks/architecture-results.md
```

This check observes real calls to the DOM converter and native event constructor
in separate, untimed workers, while still running the real parser. Complete
outputs and callback contents must match the selected measured architecture.
The intended public selection is iterative DOM for exact default strings/bytes,
and native events for files, generators, callbacks and mapping options. The
four-way tables remain architecture measurements, not a separately timed fifth
hybrid implementation.


The intermediate strict-default optimization is also preserved in
[architecture-build4-smoke.json](architecture-build4-smoke.json) and
[architecture-build4-large-smoke.json](architecture-build4-large-smoke.json).
These are one-worker development checks, not the final matrix. The corresponding
[build4 routing smoke](architecture-build4-routing-smoke.json) covers its original
nine untimed cases. The final routing artifact adds generators, explicit options,
and retained-object integrity against xmltodict after the complete 10 and
100 MiB callback parses.


Flat discard-callback RSS in these record fixtures is specific to their fixed,
small vocabulary and shallow nesting. It does not establish constant memory
for arbitrary XML: parser name/entity tables, distinct document names and
nesting can grow even when the application discards every emitted item.
